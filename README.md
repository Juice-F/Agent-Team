# Agent Team

飞书群里的产品 & 研发团队。四个机器人各管一环，把一句需求推到代码合入。

群里说一句话 → 意图识别判简单还是复杂 → 简单的当场回一句就完了；复杂的交给话题助手判断该不该立项
→ 立项后开一个话题，接力就在这个话题里进行。**一个话题 = 一个任务**，不同话题完全并行。

## 意图识别

话题助手前面还有一道岔路口（`src/router/`），拦在开话题之前，省得一句「你好」也走一遍立项需求澄清。

```
消息 ──▶ 规则匹配 ──命中──▶ SIMPLE / COMPLEX
           │
         没命中
           ▼
         分类器（小模型，只吐 {"label","confidence"}）
           │
           ├── SIMPLE 且 confidence ≥ 0.85 ──▶ 小模型答 ──▶ 大模型评分 ──┬─ ≥ 7 ──▶ 发出去，完
           │                                                          └─ < 7 ──┐
           │                                                                   ▼
           └── 其余（COMPLEX / 置信度不够 / 超时 / 报错）──────────────▶ 话题助手：开话题 → 立项需求澄清
```

规则那层是本地正则，两头都很确定的先判掉：带着动词、文件路径、链接或者超过 120 字的当 COMPLEX，
整条就是一句寒暄、客套、纯表情、问团队本身的当 SIMPLE。中间那批含糊的才花一次模型调用。

评测不过**不重答**，而是退回去开话题做立项需求澄清——和 COMPLEX 走的是同一条链。分数低说明这条
消息本来就不该被一句话打发，换个更贵的模型再答一遍只会把需求包装得更像闲聊。

整条路都往 COMPLEX 偏，就一个理由：多开一个话题只是啰嗦，把一个需求用一句话打发掉是真丢活。
所以分类器超时、报错、置信度不够、答完评测不过，一律推回原来那条链。

闸门都在 `src/router/config.ts` 里，调的时候只动这一处：

| 常量 | 默认 | 管什么 |
| --- | --- | --- |
| `simpleThreshold` | `0.85` | 分类器判 SIMPLE 时置信度得压过这条线，否则按 COMPLEX 走 |
| `classifierTimeoutMs` | `20_000` | 分类器的截止时间。模型层是拉 CLI 子进程，冷启动就得几秒，别按 API 直连的量级给 |
| `enableCascade` | `true` | 关掉就直接发小模型那版，不评测 |
| `cascadeScoreThreshold` | `7` | 评测分低于这条线就退回去开话题做立项需求澄清（满分 10） |

## 流程

```
                   ┌──────────── 验收不通过 ───────────┐
                   ▼                                  │
  clarifying ──▶ spec ──▶ coding ──▶ review ──▶ accepting ──▶ done
                             ▲           │
                             └───────────┘
                            审查不通过
```

| 阶段 | 谁干 | 干什么 |
| --- | --- | --- |
| `clarifying` | 话题助手 | 需求没说清就在话题里接着问；问清楚了交给产品 |
| `spec` | 产品 | 把需求拆成研发能照着写的方案 |
| `coding` | 研发 | 按方案改代码 |
| `review` | 审查 | 看这一轮改动：<br>通过 → `accepting`，交给产品验收<br>不通过 → `coding`，人工确认后返工。代码的问题，需求不动 |
| `accepting` | 产品 | 验收这一轮做出来的东西：<br>通过 → `done`，这个任务到此为止<br>不通过 → `spec`，需求本身得改，回去重新拆一遍 |
| `done` | — | 完成 |

两条回头路的落点不一样，因为错在不同的层：`review` 打回是实现没做对、方案还算数，只退一步；
`accepting` 打回是方案本身不对，退到 `spec` 重拆——让研发照着同一份方案再写一遍没有意义。

往前走还是往回退由那一棒自己的结论决定，图只负责说哪些走法是允许的；走图上没有的边当场就炸。

## 一棒是怎么交出去的

每一棒跑完，**在话题里 @ 下一个角色**，那个机器人收到才开工——不是进程内直接调用。
所以群里看得见接力棒传给了谁，一条用户消息也不会把整条链卡在一个事件回调里。

内容不走那条 @ 消息的文本，走**交接单**：上一棒的产出落盘在任务文件里，
下一棒开工前按目标阶段声明的 schema 验一遍才交到它手上。

任务的每一步都落盘（`.sessions/tasks/<thread_id>.json`），文件里的 `phase` 说明这一棒的状态：

| `phase` | 含义 |
| --- | --- |
| `pending` | 交接单到了还没开工，或者跑到一半被打断了 |
| `running` | 正在跑 |
| `waiting` | 跑完了，停下来等人说话（终点也算） |

进程死在半路，文件里留着的就是 `running`，下次启动扫一遍就能把它捡回来重跑那一棒。
`waiting` 的不动——那是本来就该停在那儿等人的。
