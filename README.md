# Agent Team

飞书群里的产品 & 研发团队。四个机器人各管一环，把一句需求推到代码合入。

群里说一句话 → 意图识别判简单还是复杂 → 简单的当场回一句就完了；复杂的交给话题助手判断该不该立项
→ 开一个话题，在话题里定下仓库和分支，接力就在这个话题里进行。
**一个话题 = 一个任务 = 一份自己的代码副本**，不同话题完全并行。

## 意图识别

话题助手前面还有一道岔路口（`src/router/`），拦在开话题之前，省得一句「你好」也走一遍立项需求澄清。

```
消息 ──▶ 规则匹配 ──命中──▶ SIMPLE / COMPLEX
           │
         没命中
           ▼
         分类器（小模型，只吐 {"label","confidence"}）
           │
           ├── SIMPLE 且 confidence ≥ 0.85 ──▶ 小模型答 ──▶ 大模型评分 ──┬─ ≥ 7 ──▶ 发出去，完
           │                                                          └─ < 7 ──┐
           │                                                                   ▼
           └── 其余（COMPLEX / 置信度不够 / 超时 / 报错）──────────────▶ 话题助手：开话题 → 立项需求澄清
```

规则那层是本地正则，两头都很确定的先判掉：带着动词、文件路径、链接或者超过 120 字的当 COMPLEX，
整条就是一句寒暄、客套、纯表情、问团队本身、或者整条都是碎片（`111 222 aaa bbb`）的当 SIMPLE。
中间那批含糊的才花一次模型调用。

碎片那条规则还自带回复，命中就直接发，不走后面「小模型答 + 大模型评」那条链：
认出乱码之后还去问模型是白花两次调用，而且「没看懂」这种回复很容易被评测判成敷衍再退回来，
正好绕回想避开的那条路。

评测不过**不重答**，而是退回去开话题做立项需求澄清——和 COMPLEX 走的是同一条链。分数低说明这条
消息本来就不该被一句话打发，换个更贵的模型再答一遍只会把需求包装得更像闲聊。

整条路都往 COMPLEX 偏，就一个理由：多开一个话题只是啰嗦，把一个需求用一句话打发掉是真丢活。
所以分类器超时、报错、置信度不够、小模型答不出来、评测跑不出来、答完评测不过，一律推回原来那条链。

评测跑不出来时**也退回去**，不是把没评过的那版发出去：评测本来就是拦「小模型把一个需求敷衍
过去」的那道闸，闸坏了更该退，不是放行。`route` 和 `answer` 因此都不往外抛异常，模型侧的错
在路由这层就地折成 COMPLEX / 退回——捷径走不通就走原路，不该由调用方去接它的异常。

闸门都在 `src/router/config.ts` 里，调的时候只动这一处：

| 常量 | 默认 | 管什么 |
| --- | --- | --- |
| `simpleThreshold` | `0.85` | 分类器判 SIMPLE 时置信度得压过这条线，否则按 COMPLEX 走 |
| `classifierTimeoutMs` | `20_000` | 分类器的截止时间。模型层是拉 CLI 子进程，冷启动就得几秒，别按 API 直连的量级给 |
| `answerTimeoutMs` | `30_000` | 小模型答那步的截止时间。三步都在用户看到任何反馈之前，卡得比模型自己那档 `timeoutMs` 紧 |
| `judgeTimeoutMs` | `45_000` | 大模型评测那步的截止时间，超了当评测跑不出来，退回去 |
| `enableCascade` | `true` | 关掉就直接发小模型那版，不评测 |
| `cascadeScoreThreshold` | `7` | 评测分低于这条线就退回去开话题做立项需求澄清（满分 10） |

## 流程

```
                   ┌──────────── 验收不通过 ───────────┐
                   ▼                                  │
  clarifying ──▶ spec ──▶ coding ──▶ review ──▶ accepting ──▶ done
                             ▲           │
                             └───────────┘
                            审查不通过
```

| 阶段 | 谁干 | 干什么 |
| --- | --- | --- |
| `clarifying` | 话题助手 | 需求没说清就在话题里接着问；**问清楚 + 仓库填好**才交给产品 |
| `spec` | 产品 | 把需求拆成研发能照着写的方案 |
| `coding` | 研发 | 按方案改代码 |
| `review` | 审查 | 看这一轮改动：<br>通过 → `accepting`，交给产品验收<br>不通过 → `coding`，人工确认后返工。代码的问题，需求不动 |
| `accepting` | 产品 | 验收这一轮做出来的东西：<br>通过 → `done`，这个任务到此为止<br>不通过 → `spec`，需求本身得改，回去重新拆一遍 |
| `done` | — | 完成 |

两条回头路的落点不一样，因为错在不同的层：`review` 打回是实现没做对、方案还算数，只退一步；
`accepting` 打回是方案本身不对，退到 `spec` 重拆——让研发照着同一份方案再写一遍没有意义。

往前走还是往回退由那一棒自己的结论决定，图只负责说哪些走法是允许的；走图上没有的边当场就炸。

## 在哪个仓库干活

不写死，也不配。需求在话题里聊清楚的那一刻，话题助手发一张卡片，一格由用户填：

```
┌ 填仓库 ─────────────────────────────┐
│ 明白了，就是一个本地的一页笔记…       │ ← 助手确认需求那句话
│ ─────────────────────────────────── │
│ 在哪个仓库上做？本地路径或 git 地址   │ ← 每次都一样的说明
│ ─────────────────────────────────── │
│ 仓库 [ ______________ ]   [ 确认 ]   │
└─────────────────────────────────────┘
```

**卡片只在需求定下来之后才出现**。助手那句「我明白了」是它的第一层——话和表单各占
一条消息的话，人得先看完一段字再往下找输入框，中间还隔着头像和时间。一句话就说清
楚了的需求，话题里的第一条消息就是这张卡；没说清楚的先纯文字追问，聊到清楚了再发。

不用填分支：让人敲一条分支只是多一格。拉的是仓库默认分支。

填的仓库**原样交给 `git clone`**，本地路径、`git@`、`https://` 都认，这边不做任何解析，
但点确认时会分门别类地验一遍，哪儿不对就把同一张卡片带着错误再发一次（填过的原样预填回去）：

| 情况 | 卡片上说 |
| --- | --- |
| 空着 | 仓库还没填 |
| `Vibe-Repo`、`github.com/org/repo` | 这个地址看不懂——本地路径要从盘符或 `/` 开始，git 地址要带前缀 |
| 本地路径不存在 | 路径不存在 |
| 路径指到文件 | 路径不是目录 |
| 目录在但没有 `.git` | 这个目录不是 git 仓库，先 `git init` |
| 远端 `ls-remote` 失败 | 这个仓库连不上（git 的原话折叠在里面） |

本机路径这几种自己先看一眼再交给 git：让 git 去撞，它只会回一句「不像个仓库」，
分不出是路径敲错了还是这个目录压根没 git 过，而这两件事要做的补救完全不同。

`clarifying` 是一条直线，三步走完才转给产品，缺一步都停在原地：

| 步 | 停在这儿的样子 | 走完 |
| --- | --- | --- |
| 1. 把需求问清楚 | 纯文字接着追问 | `settled`，这才把填仓库的卡片发出来 |
| 2. 用户填仓库、点确认 | 填错了在同一张卡上说哪儿不对，原样预填回去 | `repo` 落盘 |
| 3. clone 到工作区 | 拉不下来就报错 + 重发卡片，需求那部分照样留着 | 交给产品 |

顺序是死的：需求还在聊的时候不发卡片。那会儿这个需求最后落到哪个仓库、要不要做
都还没定，先摆个输入框在那儿，用户填了也是白填，聊崩了更是白拉一个仓库。

**一个仓库一份 clone**，落在**系统临时目录**下的 `agent-team/works/<仓库名>/`——
不放进项目目录，是因为它本来就不是这个代码库的东西：每台机器各拉各的，不跟着代码走，
也不指望在机器之间共享。同一台机器上同一个仓库只留一份，一个大仓库拉一次就够了；
代价是同一个仓库上并行的两个任务共用一份工作树，会看见对方改到一半的文件。

要动代码的三棒（研发、审查、验收）开工前都各自 `workspace.ensure()` 一次：**要用的时候
才现拉**，目录不在就照着任务里记的 `repo.source` 重新 clone。所以工作区是**可重建的
派生物**，不是状态，丢了不要紧、也不入库。

**闲了一天就清掉。** 每次 `ensure()` 会在 `.git/` 里盖一下「刚用过」的戳（放 `.git/`
里，角色不会在 `git status` 里看见它），同时顺手扫一遍工作区根目录，把超过 24 小时
没人开工的整个删掉——算的是「上次有人干活到现在」而不是「什么时候拉的」，所以还在
推进的任务不会被清；被清掉的是聊崩了、早就收了工的那些。24 小时比最长的一棒（研发
1 小时）宽出一个量级，撞不上正在跑的活儿。清不掉不算错：文件锁着、别人正在用都可能
让删除失败，工作区反正能重拉，不值当为了扫不干净把开工拦下来。

`src/workspace/` 对外就三件事——`check()` 验用户填的地址、`ensure()` 把目录准备好、
`dirOf()` 算目录在哪。git 怎么调、超时多少、放在哪、什么时候清、上次拉到一半剩的
半个目录怎么收拾，都关在里面；外面那几棒只想要一个能进去干活的路径。

按这个口径，任务换台机器接着跑，代码那部分是自洽的。真要分布式还差两件事：
`.sessions/` 目前只在本机磁盘上；研发那一棒的改动只留在工作区、没有提交，
重新 clone 拿到的是干净的树，diff 就丢了——得先让它跑完把改动推到任务分支上。

## 一棒是怎么交出去的

每一棒跑完，**在话题里 @ 下一个角色**，那个机器人收到才开工——不是进程内直接调用。
所以群里看得见接力棒传给了谁，一条用户消息也不会把整条链卡在一个事件回调里。

内容不走那条 @ 消息的文本，走**交接单**：上一棒的产出落盘在任务文件里，
下一棒开工前按目标阶段声明的 schema 验一遍才交到它手上。

任务的每一步都落盘（`.sessions/<thread_id>.json`），文件里的 `phase` 说明这一棒的状态：

| `phase` | 含义 |
| --- | --- |
| `pending` | 交接单到了还没开工，或者跑到一半被打断了 |
| `running` | 正在跑 |
| `waiting` | 跑完了，停下来等人说话（终点也算） |

进程死在半路，文件里留着的就是 `running`，下次启动扫一遍就能把它捡回来重跑那一棒。
`waiting` 的不动——那是本来就该停在那儿等人的。
